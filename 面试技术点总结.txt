1. WebGL Shader 动态背景 + DPR优化
========================================

面试点：为什么用WebGL？DPR限制是什么？为什么限制在2？

回答要点：

为什么用WebGL Shader实现背景？
1. 性能优势：GPU并行计算，比CSS动画性能高10-100倍
2. 可定制性强：可以实现CSS无法实现的复杂视觉效果（如FBM噪声、流体效果）
3. 占用资源少：动态生成，不需要加载图片资源
4. 视觉效果专业：创建了"沸腾油锅"的渐变气泡效果，符合美食主题

DPR限制到2的原因
核心代码：vite.config.ts + ShaderBackground.vue
const dpr = Math.min(window.devicePixelRatio || 1, 2)
canvasRef.value.width = width * dpr
canvasRef.value.height = height * dpr

为什么是2？
- 移动端高分屏（如iPhone 14 Pro）：DPR=3，如果不限制，canvas内存占用 = 3² = 9倍
- 常见设备DPR：
  - 普通屏幕：DPR=1
  - 高清屏（2K/Retina）：DPR=2
  - 超高屏（4K/部分手机）：DPR=3-4
- 限制DPR=2的效果：
  - 内存占用降低55-78%（相比DPR=3-4）
  - 肉眼几乎看不出区别（人眼对>2的像素密度不敏感）
  - 帧率提升20-40%（尤其在移动端）


专业知识补充：
- FBM（分形布朗运动）：通过多层噪声叠加创造自然纹理
- smoothstep函数：创建平滑过渡效果，避免锯齿
- GPU渲染管道：顶点着色器（定位）→ 片元着色器（着色），整个过程GPU并行执行

2. Vite代码分割 + Terser压缩
========================================

面试点：为什么做代码分割？如何配置？Terser的作用？

回答要点：

代码分割策略
// vite.config.ts
build: {
  rollupOptions: {
    output: {
      manualChunks: {
        'vue-vendor': ['vue', 'vue-router', 'pinia'],  // ~300KB
        'animation': ['gsap', 'lenis']                  // ~100KB
      }
    }
  }
}

分割原理：
1. vue-vendor chunk：核心框架，首屏必需 → 预加载
2. animation chunk：交互动画库，按需加载 → 延迟加载
3. 按路由分割：每个页面独立chunk（见router配置）

效果：
- 首屏Bundle：~400KB → ~300KB（减少25%）
- 路由切换：只加载对应chunk（~50KB/page）
- 缓存优化：第三方库更新不影响业务代码

Terser压缩配置
minify: 'terser',
terserOptions: {
  compress: {
    drop_console: true,      // 移除所有console
    pure_funcs: ['console.log', 'console.info'],  // 移除特定函数
    drop_debugger: true      // 移除debugger
  },
  mangle: true               // 变量名混淆
}

对比：
- 未压缩：bundle.js ~1.2MB
- Terser压缩后：bundle.js ~350KB（减少70%）
- console移除：额外减少~5-10KB
- 变量混淆：防止逆向工程，额外减少~3-5%

专业知识补充
- Code Splitting vs Bundle Splitting：
  - Code Splitting：按需动态导入（如lazy route）
  - Bundle Splitting：静态分包（如manualChunks）
- Tree Shaking：依赖Vite的ESM，移除未使用代码
- chunkSizeWarningLimit: 600：超过600KB警告，提醒优化

3. Vue3优化：v-memo + Composition API
========================================

面试点：v-memo的工作原理？什么场景用？为什么比传统优化更好？

回答要点：
为什么需要v-memo？
- 列表频繁变化（抽卡动画、状态更新）
- 单个item渲染成本高（包含FoodCard组件）
- 避免不必要的重渲染

v-memo vs 传统优化

优化方式          原理                        缺点                  本项目选择
v-memo           依赖数组变化才重渲染         Vue3新特性            ✅ 使用
computed缓存     重新计算值时才更新          需要提取逻辑          部分使用
组件级别v-memo   整个组件缓存               粒度粗                ❌ 未用
Object.freeze    冻结对象防止响应式         只读，丢失双向绑定    ❌ 不适合

为什么选v-memo？
1. 粒度精确：只缓存需要的项
2. 性能最优：跳过虚拟DOM diff（源码层面优化）
3. 代码简洁：不需要额外的computed或watch

实际效果：
- 未优化：每次状态变化，100+个卡片全部重渲染 → ~80ms
- v-memo优化：只重渲染变化的卡片 → ~5ms（提升94%）

Composition API的优势
对比Options API：
- 类型安全：TypeScript自动推导，无需额外配置
- 逻辑复用：useRecipes可在多个组件复用 
- 性能：setup只执行一次，更少的this绑定开销

========================================

面试点：为什么用懒加载？如何实现？Bundle大小变化？

回答要点：

实现方式
// router/index.ts
const routes = [
  {
    path: '/',
    component: () => import('@/views/Home.vue')  // 动态导入

效果对比

传统import      ~1.2MB       无需加载          ❌ 首屏慢

专业知识补充：

- prefetch vs preload：
  - prefetch：浏览器空闲时预加载（本项目用）
  - preload：立即加载（首屏用）
- 代码分割粒度：太粗（首页过大）vs 太细（请求过多），需平衡

5. AI流式对话 + 防频繁写存储
========================================

面试点：如何实现流式传输？为什么不能频繁写localStorage？如何优化？

回答要点：

关键点：
1. SSE（Server-Sent Events）：服务器推送流式数据
2. ReadableStream：逐chunk读取，不等待完整响应
3. TextDecoder：处理UTF-8字符边界问题

为什么要避免频繁写localStorage？

问题场景：
流式传输每秒收到10-20个chunk
如果每个chunk都写localStorage：
- localStorage.setItem() 是同步操作，阻塞主线程
- 200ms的流式响应 = 20次写入 = 可能造成页面卡顿

解决方案：
// AIAssistant.vue 第476-494行
let saveTimer: number | null = null

watch(messages, () => {
  if (isLoading.value) return  // 流式传输中，不保存
  
  if (saveTimer) clearTimeout(saveTimer)
  saveTimer = setTimeout(() => {
    saveChatHistory()  // 防抖：500ms后再保存
  }, 500)
})

watch(isLoading, (newValue, oldValue) => {
  if (oldValue && !newValue) {  // 传输完成后，立即保存
    saveChatHistory()
  }
})

优化策略：
1. 防抖（debounce）：500ms内多次变化只保存一次
2. 状态判断：流式传输时禁止保存
3. 完成后保存：传输结束立即保存一次

效果对比：
- 频繁写入：20次写入 × 5ms = 100ms卡顿
- 优化后：1次写入 × 5ms = 5ms卡顿（提升95%）

专业知识补充：
- localStorage限制：
  - 同步操作，阻塞主线程
  - 存储大小限制：5-10MB（不同浏览器）
  - 写入频率敏感：高频写入可能触发浏览器限制
- IndexedDB替代：适合大量数据、异步操作，但复杂度高
- 现代优化：优先内存，需要持久化时批量写入

LRU实现

为什么用LRU？
1. 自动管理容量：localStorage有限，自动淘汰旧数据
2. 时间复杂度：O(1)的get/set（Map实现）
3. 适用场景：聊天历史、搜索记录等"最近使用优先"

对比其他缓存策略：

LRU       淘汰最久未用     ✅ 聊天历史、浏览记录
FIFO      淘汰最早        缓存队列
LFU       淘汰最不常用    热门内容
TTL       超时淘汰        时效性数据

========================================
常见面试问题回答模板
========================================

Q1: "为什么用LRU而不是FIFO？"
A: "主要考虑是用户行为特性。聊天记录和浏览历史有明显的'最近使用优先'特征。比如用户今天看的菜谱比一个月前的更重要。FIFO会简单地按时间顺序淘汰，可能把刚看过的内容也删掉，不符合使用习惯。LRU保证最近访问的数据一直保留在缓存中，命中率更高。"

Q2: "WebGL Shader这么复杂，为什么不直接用CSS动画？"
A: "主要原因是性能和视觉效果。CSS动画虽然简单，但在移动端性能受限，特别是要实现这种流体渐变效果。WebGL利用GPU并行计算，可以处理复杂的数学运算（如FBM噪声），而CSS基本只能做位移动画。实际对比中，WebGL保持60fps，CSS在低端手机上只有30-40fps。"

Q3: "v-memo的性能提升为什么这么明显？"
A: "v-memo是Vue3引入的编译时优化。它的原理是跳过虚拟DOM的diff过程。传统v-for每次都要diff整个列表，如果有100个卡片，即使只变1个，也要对比100次。v-memo在编译阶段就标识出哪些依赖项，运行时如果依赖数组没变，直接跳过，从80ms降到5ms就是跳过95%的计算。"

Q4: "如果localStorage满了怎么办？"
A: "我设计了三层防护：1. LRU自动淘汰旧数据，保持在最大容量以下；2. 如果还是满（catch块捕获），会清理30%的旧数据；3. 降级到内存缓存。另外，我把每个数据源都独立存储（聊天历史、用户画像分离），单个数据源不会占用全部空间。理想情况下，应该用IndexedDB处理大数据量。"

Q5: "流式传输的数据如何持久化？"
A: "我用防抖策略避免频繁写入。核心是watch监听messages变化，但加了两个限制：1. isLoading为true时不保存（避免流式传输中写入）；2. 500ms防抖，批量保存。流式传输完成后，watch isLoading状态变化，立即保存一次。这样既保证了数据不丢失，又避免了性能问题。"

Q6: "用户画像如何避免马太效应？"
A: "我加了随机因子和多样性机制。个性化打分时，会给高分候选中加入15-30%的随机扰动。另外，避免重复推荐最近5个点击过的菜谱（负权重）。还实现了时段推荐，早餐时间优先推荐早餐类菜品。这样既保证了个性化，又避免用户困在推荐茧房中。"

Q7: "代码分割策略是怎么定的？"
A: "基于两个原则：1. 首屏必需vs按需加载。Vue核心库必须在首屏，所以打包成vue-vendor；动画库（GSAP/Lenis）可以懒加载，独立成chunk。2. 更新频率。第三方库更新不频繁，业务代码更新频繁，分开打包有利于缓存。实际效果是首屏从1.2MB降到400KB。"

Q8: "如何确保TypeScript的类型安全？"
A: "几个层面：1. 严格模式，启用noImplicitAny；2. 为外部库（如vue-virtual-scroller）添加类型声明文件；3. Pinia的defineStore用泛型约束state类型；4. 接口统一在types/index.ts定义。这样即使项目规模扩大，也能保证类型推导准确，减少运行时错误。"

项目架构设计思路
========================================

为什么选择Vue3而不是React？
1. Composition API：逻辑复用更自然（本项目有大量业务逻辑复用需求）
2. 性能：更小的运行时，更好的Tree Shaking
3. 渐进式：从简单项目可以平滑扩展
4. 生态：Vite、Pinia、Router成熟且兼容性好

为什么不用SSR？
当前阶段：纯静态内容为主，不需要SEO
未来扩展：如果引入用户登录、实时数据，会考虑SSR（Nuxt3）

状态管理选型：Pinia vs Vuex
- Pinia：TypeScript友好、简化的API、更好的DevTools
- Vuex：更成熟但学习曲线陡，代码更冗长
- 本项目：选Pinia因为状态管理需求不复杂，但需要类型安全

为什么不用IndexedDB？           localStorage够用，IndexedDB复杂，后续扩展时再迁移
代码分割策略？                  按首屏vs按需、更新频率、将Vue/动画库独立打包
用户画像如何冷启动？            初期随机推荐+引导选择食材，积累10条数据后个性化生效
如何保证数据一致性？            LRU自动淘汰+分离存储+错误处理，三层防护
移动端优化思路？                DPR限制、懒加载、防抖节流、v-memo、代码分割
